# Фронтенд страницы «Крафт» — правила

Страница `craft.html` построена на Preact + htm без сборки (`public/vendor/*`), стили — `public/css/next.css`. Любая правка интерфейса следует этим правилам, чтобы страница не превратилась обратно в нагромождение.

## Архитектура
- **Логика отдельно от интерфейса.** Расчёты — чистые функции в `logic/*.js` (без DOM, с юнит-тестами в `tests/next*.test.js`): `acquire` (план закупки), `profit`, `manual` (свои цены, план продажи), `cityPrices`, `factionPlan`, `stack`. Компонент только показывает и передаёт правки.
- **Состояние — в хранилищах** (`createStore` из `lib.js`): `settings` (параметры), `list` (крафт-лист), `nav`, `calc-store`, `scan`, `faction`, `lazy`. Компоненты подписываются через `useStore`. Никаких глобальных переменных и ручного DOM.
- **Один компонент — одна задача.** Повторяющиеся куски выносятся в общий компонент (`ui.js`: метки предмета, города, переключатели; `citylist.js`: панель «Все города»), а не копируются в разные вкладки.
- **Стеки позиций.** Крафт-лист и стек калькулятора — один и тот же объект (`list.js` → `createStack`, расчёт — `listcalc.js` → `createStackEngine`, общие компоненты — `stack-ui.js`). Новая функциональность стека пишется один раз для обоих. Стек калькулятора — копия активных позиций листа (`stack-open.js`), правки в нём лист не меняют.
- **Свои цены материалов** — общее хранилище `prices.js` (единая цена, цены городов, лог лотов) для калькулятора, листа и стека; применяются через `logic/adjust.js`.
- **Вкладки инструментов:** `scan.js`, `calc*.js`, `faction.js`, `lazy.js`; общий каркас — `app.js`; крафт-лист — `dock.js` + `listcalc.js`.
- **Запросы** — только через `apiGet/apiPost` (`lib.js`); общие параметры расчётов — `commonParams()` из `settings.js`. Бэкенд без необходимости не трогаем.

## Дизайн
- Цвета, отступы, радиусы — только переменные из `:root` в `next.css`; своих цветов в компонентах нет. Хорошее — `--good`, плохое — `--bad` (мягкие), акцент один — `--accent`.
- Тир, зачарование, качество — компонент `Tags`; город — `CityPill`; значок предмета — `Glyph`. Цифры — с `fmt`/`signed`, знак и цвет вместе.
- Принцип «сначала главное»: вердикт/итог сверху, детали — во вкладках и раскрывающихся панелях (`details`), редкие настройки — в «Ещё». Серые поля «своя цена» не расставляются по таблице, а прячутся в раскрывающиеся панели.
- Поле ввода со своим значением: серым — рыночное (placeholder), рамка акцентом — когда вписано своё.
- Новый элемент должен работать на телефоне, в тёмной и светлой теме и с клавиатуры (`aria-*`, подписи).

## Тесты
- Каждая новая логика — юнит-тест; каждый пользовательский сценарий — e2e в `e2e/craft-next.spec.js` (десктоп и телефон).
- Прежняя страница — `craft-classic.html` (временно), её код и тесты не расширяем.

## Запросы к серверу
- Сервер пускает не больше **60 запросов в минуту** на `/api` с одного адреса — независимо от источника данных (краулер или AODP). Все запросы страницы идут только через `apiGet`/`apiPost` из `lib.js`: общий бюджет (`apiLimits`, 40 в минуту, лишнее ждёт очереди), кэш и дедупликация (`{ ttl }` — для расчётов позиций одинаковы у листа, стека и калькулятора), автоповтор при 429.
- Новый расчёт запускай с `ttl`; не создавай второй движок расчёта на те же позиции — используй `createStackEngine` (стек калькулятора считается, только пока открыт).

## Оборот плащей
- Логика — `logic/turnover.js` (`turnoverPerDay`, `turnoverInfo`, `marketCap`); показ — общий компонент `Turnover` (`ui.js`). Оборот виден в плане (колонка «Оборот/день», метка «потолок»), в карточках крафт-листа и стека, в таблице продаж стека; в одиночном калькуляторе он уже есть в итоговой панели и во вкладке «Продажа».
- Позиции из плана несут `dailyVolume` (цифра плана — та же, что задаёт потолок); у остальных оборот берётся из расчёта калькулятора.
- Потолок плана = оборот × окно истории. Переключатель «Игнорировать» (`factionStore.ceil`) снимает рыночный потолок, свои лимиты остаются; план предупреждает, что партия продастся дольше окна. `buildPlan` ограничен `MAX_PLAN_STEPS`, чтобы опечатка в очках не вешала страницу.
- **План продажи по городам** — одна таблица `cityplan.js` (`CityPlanTable`) для одиночного калькулятора и позиций стека; она ничего не хранит: состояние правок (`toggles`, `manualQty`, `cityPrices`, `strategy`) и действия приходят снаружи. Правки — чистые функции `logic/planEdit.js`. В стеке правки лежат в позиции (`item.plan`) и сразу идут в профит (`applyItemPlan` в `useStackData`); отдельного окна «изменить план» нет — всё правится в карточке.
- **Сводная закупка стека** — `stack-shopping.js`: одинаковые материалы включённых позиций складываются; у каждого — города закупки, своя цена (или лог лотов, если включён — `OwnPrice` из `calc-buy.js`) и панель «Все города» со всеми активными городами, даже без рыночных цен. Ключ своей цены материала — id **с зачарованием** (`queryId`): плащ .1 и .3 — разные материалы. Своя цена закрывает и материал без рыночной цены, и компоненты крафта/переработки (ткань, кожа, сырьё), и готовую базу .0 (`logic/manual.js`, `logic/cityPrices.js`).
- **Скан и «чары после крафта»** — тумблер шлёт `enchantMode=auto`: сервер сам выбирает «после крафта» только там, где оно выгоднее прямого не меньше чем на 7%; у строки есть флаг `after` — по нему, а не по режиму скана, решается, считать ли позицию «после» в калькуляторе и листе (`isAfter` в `scan.js`).
- **Города вне расчёта** (по умолчанию Caerleon и Brecilien): страница шлёт `infoCities`, сервер возвращает по ним цены и оборот с `inactive: true`; они видны везде, где показываются города (`cityRows`, `CityPlanTable`, таблица цен готового), но в выбор закупки, автоплан и профит не входят, пока не включены в параметрах, не отмечены галочкой «В плане» или в них не вписана своя цена.
- **Чёрный Рынок в калькуляторе** — та же схема, что у городов «вне расчёта»: тумблер «Показывать Чёрный Рынок» (`settings.blackMarket`) только решает, запрашивать ли его вообще (краулер его не собирает — это всегда живой запрос к AODP, поэтому по умолчанию тумблер выключен и запроса нет). Когда тумблер включён, ЧР виден в таблице цен готового предмета и в плане продажи по городам (`inactive: true`), но не выбирается автоматически ни мгновенной продажей, ни планом — его включают галочкой «В плане», как Caerleon/Brecilien. Сервер: `server.js`, секция `/api/craft-calc` — BM-строки строятся отдельно от активных городов (`infoSellPrices`, отдельный вызов `computePatientSell` с `queryCities: ['Black Market']`), а не подмешиваются в общий расчёт.
- **«Ещё сравнения»** (`calc-sell.js`) — таблицы «По качеству» и «По тирам» объединены в один свёрнутый по умолчанию блок внизу вкладки «Продажа» (`details.more`, стиль в `next.css`); раньше это была карточка под продажей и отдельная третья вкладка калькулятора — расходовали место на экране, хотя открывают их редко. Клик по строке тира по-прежнему переключает предмет.
- **Общий порог «зачарки после крафта»** — `logic/afterCraft.js` (`AFTER_CRAFT_MIN_GAIN = 0.07`, `afterCraftWins(profitDirect, profitAfter)`): используют `logic/stack.js` (крафт-лист, стек калькулятора) и `logic/factionPlan.js` (фракционный план); `server.js` (скан, `resolveAfterChoice`) держит то же число отдельным `ENCHANT_AFTER_MIN_GAIN` — ESM и CommonJS модуль напрямую не делят, значение продублировано вручную с комментарием-ссылкой. Раньше план сравнивал голую себестоимость материалов на 5%, остальные — профит на 7%: один и тот же предмет мог получить разный совет на разных экранах. Теперь везде один вопрос («на сколько выгоднее по профиту») и один порог.
- **Уведомление «в крафт-лист»** — `dock.js` (`DockNotice`, `list.js` — `listNotify`, `notifyListAdd`): карточка у дока (значок, название, метки, количество; массовое добавление — «N позиций … из плана») вместо общего тоста в центре экрана — эти два уведомления раньше дублировали друг друга при каждом добавлении, оставлен только новый. `addToList(item)` уведомляет сама; массовые операции (`lazy.js` addAll, `faction.js` send) зовут `list.add`/`list.replaceFaction` напрямую и один раз `notifyListAdd({ kind: 'batch', count, label })` — иначе при добавлении плана целиком вспыхнуло бы по карточке на каждую позицию. Сам док (кнопка «Открыть») перенесён в правый нижний угол и увеличен — раньше был по центру внизу тонкой плашкой.
- **Баг «Загрузка…» навсегда в углу страницы** — `main.js` рендерил приложение поверх статической заглушки из `craft.html`, не убрав её: Preact не чистит контейнер сам, если в нём уже есть чужая разметка. Заглушка так и оставалась в DOM рядом с приложением на каждой загрузке страницы (это видно на любом скриншоте этой страницы, сделанном раньше в этом разговоре — просто не бросалось в глаза). Теперь `main.js` чистит `#app` перед первым рендером.
- **Док крафт-листа: выравнивание по краю контента, не по краю окна.** На широком мониторе центрированный контент (`.layout`, `max-width: 1160px`) кончается задолго до правого края окна — на 1920px между последней карточкой и краем экрана было 386px пустоты, на 2560px — 706px; кнопка «под рукой» не ощущалась. `.dock`/`.dock-notice` теперь используют `right: max(18px, calc(50vw - 556px))` — правый край дока стоит вровень с правым краем `.card`/`.wrap` на любой ширине (556 = половина `max-width` минус его отступ 24px); на узких экранах, где контент и так во всю ширину, работает нижняя граница `max()` — прежний отступ 18px. Проверено измерением `boundingBox()` на 900/1160/1400/1920/2560px и e2e-тестом.
- **Свежесть данных** — окно «Свежесть данных» (кнопка в крафт-листе, в стеке калькулятора, во фракционном плане и в одиночном калькуляторе): показывает по каждому городу ровно те позиции, по которым у самого КАЛЬКУЛЯТОРА нет данных для расчёта — не отдельный порог «устарело N дней», а буквально тот же критерий, что использует расчёт. Идея пришла от пользователя: если игрок уже отсканировал город и цена лежит в краулере, зачем окну снова просить пересканировать его только потому, что прошло много часов — важен факт «есть чем считать», а не возраст.
  Сервер (`server.js`, `freshnessOf`) переиспользует НАПРЯМУЮ те же функции, что использует `/api/craft-calc`, а не повторяет их логику: `materialCitiesWithData` зовёт `materialPriceQuotes` (тот же путь, что цена материала — сделка в окне «История сырья»/`materialHours`, иначе любой когда-либо записанный снимок цены), `selfCitiesWithData` зовёт `cityStats` (тот же путь, что терпеливая продажа `byCity` — только сделки в окне «История гира»/`days`, снимок цены здесь не считается). Материалы и «сам предмет» (гир/плащ) по этой причине проверяются по-разному — как и в калькуляторе: `kind: 'self'` для готового предмета, `kind: 'material'` (по умолчанию) для всего остального; `logic/freshness.js` (`collectIds`/`collectAllIds`/`collectFactionIds`) помечает это при сборе id из ответов `/api/craft-calc`/`/api/faction-plan`. `materialHours`/`days` окно не хранит отдельно — берёт `settings.get().mhist`/`.hist`, те же параметры, что уже отправляют в `/api/craft-calc` через `commonParams()`.
  Результат бинарный по городу — `byCity: { Город: { stale: true|false } }`, без возраста цены/сделки: возраст ничего не решает (терпеливой продаже не помогает свежий ценник без сделок, а мгновенной — не мешает старая сделка при свежей цене), поэтому единственный полезный сигнал — сам факт «есть чем считать по этому городу или нет». Своя цена (`manual_prices`) закрывает «нет данных» сразу для всех городов, как и раньше.
  Список сгруппирован ПО ГОРОДАМ (`byCityGroups` в `freshness.js`): город без единой позиции не показывается; один и тот же предмет может попасть в несколько городских секций — «Обновить» на любой из них чинит его везде разом (сервер обновляет все запрошенные города за один живой запрос в AODP, `/api/freshness/refresh`, POST, до 60 id за раз). Строка позиции — минимальная: значок+название+теги тира/зачарования (`MaterialName` из `ui.js`, клик копирует название для поиска на аукционе), поле своей цены (`ManualPriceInput`, дебаунс 700мс), кнопка «Обновить» — никакой информации о возрасте или количестве городов у предмета в строке нет, это заведомо решено самой группировкой по городам.
  **Метка качества** — только у самого предмета (`kind: 'self'`), не у материалов: `MaterialName` получила необязательный `quality` (раньше не принимала его вообще — ни один из старых вызовов, все на материалах, в этой метке не нуждался), `byCityGroups` передаёт `it.quality` только когда `names.get(it.id).kind === 'self'`, иначе 0 — у материалов сайт всегда считает по Обычному качеству, метка на каждой строке была бы просто шумом, не информацией (то же решение, что и в остальном сайте — калькулятор, крафт-лист, скан показывают качество только у гира, не у сырья). Без неё разные качества одного и того же предмета (например, капюшон .3 «Отличное» и «Знаток») были неотличимы друг от друга в окне свежести.
  **Переключатели городов прямо в окне** (`.fresh-toggles`) — своё состояние `enabledCities` в `freshnessStore` (по умолчанию все семь, запоминается в браузере, `albion_next_freshness`), отдельное от общего списка активных городов в параметрах: можно на время сузить окно до тех городов, куда реально собираешься идти сканировать, не трогая настройки расчёта. Переключение сразу перезапрашивает `/api/freshness` с новым списком городов (если окно открыто и есть позиции); нельзя выключить последний город.
  Название «самого плаща» (finishedId) и герб/сердце без единой цены — как раньше: каталог названий гира есть только у клиента (`selfLabel`/`finishedLabel` резолверы, передаются в `collectIds`/`collectFactionIds`), `partQuote` на сервере всегда отдаёт `{ id, label, price: null, ... }`, а не `null` целиком, если цены нет вообще. То же самое пропустили для базы .0 при «чары после крафта», когда её покупают, а не крафтят (`eac.baseBuy`, `d.itemId` — тот же гир, что и главный self-предмет строки, просто без зачарования): резолвилась только через `d.names[d.itemId]`, а сервер отдаёт названия в `d.names` исключительно для материалов, не для гира — строка показывала голый id (`T5_HEAD_LEATHER_SET3` вместо «Капюшон убийцы»). Добавлено падение на `selfLabel(d)`, как и у главного self-предмета строки.
  Окно (`.modal-wide`) раскладывает города карточками в ряд (`.fresh-cities`, CSS grid, колонки от 250px), а не аккордеоном; карточка растёт по содержимому без своего скролла (раньше у `.fresh-city .fresh-list` был `max-height: 280px; overflow-y: auto`, из-за чего для длинного списка по городу приходилось скроллить сначала карточку, потом окно — убрано). По просьбе пользователя убран и скролл у самого окна: на широком экране (`.fresh-scrim`, `min-width: 461px`, `next.css`) `.modal .scroll` больше не имеет своего `overflow`/`max-height` — окно растёт по содержимому целиком, а скроллится сама подложка окна (`.modal-scrim.fresh-scrim { overflow-y: auto }`), как обычная страница, если контент выше экрана; раньше это была третья, отдельная от подложки коробка со своим скроллбаром внутри (`min(900px, 92vh)`), хотя вокруг неё в подложке оставалось пустое место. Правка ограничена классом `.fresh-scrim` (только у этого окна) и работает от 461px — на телефоне (≤460px) окно остаётся донной шторкой со своим потолком высоты (`min(84vh, 100%)`) и скроллом внутри, как и было: обычный мобильный паттерн, безопаснее с `position: fixed` на маленьком экране, отдельно не переделывался. Сетка — `auto-fit`, не `auto-fill`: с `auto-fill` при малом числе занятых городов (например, 2 из 7) браузер всё равно резервировал 4+ пустых колонки под невидимые карточки и не давал занятым вырасти шире минимума (250px) — строка внутри такой узкой карточки сжимала имя почти до нуля, и оно налезало на соседнее поле цены (Playwright ловил это как перехват клика). `auto-fit` схлопывает пустые колонки и отдаёт их ширину реальным карточкам через `1fr`; при полных семи городах ведёт себя как `auto-fill` (пустых колонок и так нет). Найдено и проверено прямым измерением `boundingBox()`/`getComputedStyle` в одноразовых скриптах, не на глаз.
  Строка позиции (`.fresh-row`) — два яруса, не один ряд: имя+теги (`MaterialName`) на всю ширину карточки сверху, своя цена и «Обновить» (`.fresh-actions`) прижаты вправо снизу. Изначально сделал одной строкой (`grid-template-columns: 1fr 92px auto`) — на моковых данных e2e (короткие имена) выглядело нормально, но на реальных данных живого сервера с длинными названиями (например, «Капюшон убийцы (знаток)») при 4 карточках в ряд на колонку имени оставалось ~40px, и имя переносилось по буквам, вылезая за карточку.   **План фракции** (`server.js` `/api/faction-plan`, `logic/factionPlan.js`) — свой независимый путь: `capeDirect`/`cape0` (крафт плаща-ингредиента напрямую на нужном уровне vs. `.0`+руны) были и остаются отдельной парой, сравниваемой через `afterCraftWins`, но `cape0` заменён на `capeByLevel` — цену плаща-ингредиента на КАЖДОМ уровне `0..enchant−1` (эти цены уже были в `materialQuotes`, доп. запросов не потребовалось — `quoteFor(lvl)` уже была общей для любого уровня). `computeRow` (клиент) сам гоняет `enchantChainCandidates` по `capeByLevel`+`runes`, победитель — `winner`; своя цена (`mat:<id>`) действует на любой уровень входа, не только на `.0`. Старые фикстуры без `capeByLevel` — запасной путь на один вход `.0`, как раньше. `faction.js`: панель своих цен показывает поле на каждый уровень входа (не только «Плащ .0»), у строки — пометка «(вход .N)», если выигравший путь начался не с нуля.
  **Скан** (`server.js` `/api/unified-scan`) — полный обход каталога: добавление входа не с нуля стоит дороже, чем в калькуляторе/плане фракции, — цена входа СВОЯ НА КАЖДОЕ КАЧЕСТВО (1–5), а себестоимость строки скана исторически не зависела от качества вообще (только продажа). Обсудили с пользователем — сделано опцией `chainEntry=true` (по умолчанию выключено, как и `materialLiquidity`/`confidenceMaterials`): включена — сервер батчем читает `sell_price_min` промежуточных уровней по всем качествам (`entryPriceOf`, один `readPrices` на весь скан, не по одному запросу на комбинацию) и, ТОЛЬКО внутри перебора качеств (`for (const quality of ALL_QUALITIES)`), для комбинаций «после крафта» с `enchant >= 2` пересчитывает кандидатов через `enchantChainCandidates(entryCosts, stepCosts, c.enchant)`, используя более дешёвый, если он есть; строка получает `enchantEntryLevel`. Выключена — поведение и производительность те же, что были (полная цепочка с нуля, себестоимость одна на всю комбинацию, без доп. запросов). UI: тумблер «Вход в цепочку не с нуля» (`scan.js`, `scanStore.chainEntry`) виден только при включённой «Зачарке после крафта»; у строки — та же пометка «(вход .N)», что и в плане фракции.
  **UI выбора рецепта (ответ пользователя #3 — только в калькуляторе одной вещи)** — исходная идея пользователя была про рецепты именно в контексте одиночного расчёта, поэтому дропдаун и тумблер сделаны только там (у плана фракции и скана — табличный интерфейс, туда добавлена только короткая пометка «(вход .N)» у строки, без выпадающего списка). `logic/enchantChain.js`: `applyChainChoice(data, choice)` — пересчитывает уже полученный ответ `/api/craft-calc` НА МЕСТЕ (без нового запроса) по кандидату из `eac.candidates`, тем же приёмом, что и своя цена (`logic/manual.js`). `calc-store.js`: `chainChoice` (`{ entryLevel, forceMain }`) — своё для позиции (сбрасывается при смене предмета, как и своя цена), `setChainEntry`/`setForceMain`, применяется в `derive()` ДО `applyManualPrices` (чтобы своя цена уже видела выбранный вход через `eac.chainEntryLevel`/`candidates`, которые `manual.js` и так читает обобщённо). `calc-buy.js`: `ChainChoice` — дропдаун (виден только когда есть из чего выбирать, `candidates.length > 1`; вариант «Автовыбор» возвращает серверный выбор) плюс тумблер «Только основной рецепт» рядом (форсирует вход `.0`, дропдаун при этом блокируется) — оба в панели «Зачарование после крафта».
- **Смешанные рецепты, покупка готового уровня, профили крафта.** Пользователь уточнил, что имел в виду под «входом в цепочку»: не покупку готового `.1`/`.2` на аукционе (это я реализовал по-своему), а три РЕЦЕПТА крафта одной вещи: (A) прямой — сразу на целевом уровне из зачарованного сырья `.N`; (B) `.0` из обычного сырья + все шаги рунами/душами/реликтами; (C) смешанный — база сразу на уровне `.L` из зачарованного сырья `.L`, а шаги `.L+1…N` докручиваются рунами/душами/реликтами. Выигрывает вариант, дающий ≥7% профита сверх прямого крафта (базой сравнения оставлен прямой — простейший, без десятков тысяч рун; тот же порог, что и раньше). Покупка готового `.L` осталась, но отдельной опцией.
  **Сервер** (`/api/craft-calc`): `craftEnchant=L` — база крафтится на уровне `L` (`recipeEnchant = L`, шаги только `L+1…цель`, `eac.baseLevel`); `buyReady=true` — рассматривать покупку готового (`intermediateLevels` для базы `.0`, `baseData` для `L>0`); без него покупка не считается. `eac.readyItems` — id готовых уровней для окна свежести. Внутри ответа вход на самом уровне базы для клиента — «рецепт базы» (`chainEntryLevel 0`), покупка — только уровни выше базы (`relLevel`), поэтому весь клиентский код про `chainEntryLevel > 0` остался как был. **Скан** (`/api/unified-scan`): `mixed=true` — для «после крафта» считаются базы `.0…L−1`, берётся самая дешёвая (себестоимость от качества не зависит, доп. запросы только за зачарованным сырьём); `chainEntry=true` — покупка готового (цена по качествам), теперь может сочетаться с гибридом: вход на уровне L — дешевле из «скрафтить базу» и «купить готовый». Строка: `enchantBaseLevel` (уровень базы гибрида) / `enchantEntryLevel` (куплен готовый).
  **Клиент.** `logic/stack.js` `pickAfter(item, pair)` — среди `pair.after` (база .0) и `pair.hybrids[L]` берётся самый выгодный по профиту, дальше 7% против прямого; результат — `{ use, level, data }`, `decideAfter` осталась обёрткой. `listcalc.js` — при `settings.mixedRecipes` (по умолчанию включено) для позиции с зачаркой считаются гибриды `L=1…enchant−1`, у позиции появляется `craftEnchant`. `calc.js`/`calc-store.js` — те же гибриды для одиночного калькулятора (`c.hybrids`), `logic/enchantChain.js` `pickVariant` выбирает вариант (автовыбор — самая дешёвая себестоимость; ручной — `chainChoice.baseLevel`; «Только основной рецепт» — база .0), дальше идёт прежняя цепочка `applyChainChoice` → `applyManualPrices`. `calc-buy.js` `ChainChoice` — один дропдаун «Рецепт» (автовыбор / база .0 / база .L / купить готовый .L, у вариантов без цен пункт заблокирован) плюс тумблер «Только основной рецепт». Настройки (`params.js`, «Ещё»): «Смешанные рецепты зачарования», «Покупка готового уровня» (уходит в запрос как `buyReady`); в скане два отдельных тумблера с теми же названиями. План фракции гибриды уже умел: `capeByLevel` — это и есть плащ-ингредиент на каждом уровне (база на `.L` + оставшиеся руны).
  **Окно «Свежесть данных»** теперь собирает материалы ВСЕХ вариантов, а не только победившего: без цены на какой-то материал вариант молча выпадал бы из сравнения, и обновить его было бы нечем. `collectAllIds(results, selfLabel, pairs)` (прямой, «после», все гибриды каждой позиции), `collectVariantIds` (одиночный калькулятор), `collectIds` добавляет `eac.readyItems`, `collectFactionIds` — прямой + все `capeByLevel` + руны независимо от выбранного пути.
